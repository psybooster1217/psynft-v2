### META‑1 (High, operational): the metadata host is gone · FIXED IN REPO, PIN REQUIRED

**What's wrong.** V1's `baseUri` is `https://red-literary-tiglon-645.mypinata.cloud/ipfs/bafybeia5k…/`.
That hostname returns **NXDOMAIN** from both Google and Cloudflare DNS‑over‑HTTPS (2026‑10‑10).
The `image` field inside all 34 metadata files points at the same dead host. The runbook,
`.env.example` and the sandbox all deployed with that URL, so V2 would have launched with no
resolvable art. The content itself is intact: all 34 metadata files and all 34 images (about 156 MB
across six image folders) load through `gateway.pinata.cloud`
(`audit/2026-10/raw/image-availability.txt`).

**Fix.** `metadata/v2/` holds the 34 files with only the host prefix replaced by `ipfs://`. A
script asserts every other byte is unchanged. The folder is packed as a CAR file
(`metadata/psyc-metadata-v2.car`) with root CID **`bafybeib2aqk4vcfbpgs7aoyk6z6pk5zfcli6qjuvuqohdsdriexeji6m3i`**.
`metadata/verify-pinned.mjs` checks a pinned copy byte for byte and checks every image resolves.
`.env.example` now deploys with `ipfs://<CID>/`, and the contract enforces the trailing slash
(PNFT‑04).

**Remaining (manual).** Pin the CAR and the six image folders on two services, then run the verify
script through two gateways ([metadata/README.md](../metadata/README.md)). This is a hard gate in
the runbook.

### PNFT‑01 (Medium): approvals were not consumed · FIXED

**What's wrong.** V1/V2 kept a `core` approval live until its expiry even after it had been used.
This had two effects:
1. **Corrected approvals were blocked.** After A→B under a 30‑day approval, core could not approve
   B's next move for 30 days (`"Transfer Request Currently Active"`).
2. **A used approval could revive.** Approve to B → A transfers to B → owner disables controls →
   B transfers to C → owner re-enables controls. Inside the window, C could send the token back to B
   with no new core decision.

**Fix.** An `_update` override deletes the approval whenever a token changes hands or is burnt.
Mints are skipped, so batch gas is unchanged. The clearing runs after the controlled-transfer check
and before any `onERC721Received` callback.

**Tests.** 7 regression tests (`test/AuditOct2026.t.sol`, `test_PNFT01_*`), fuzzing
(`testFuzz_ControlledTransferGate`) and invariant I5 ("approvals are single-use").

### OPS‑02 (Medium): V1 stayed mintable after cutover · FIXED

**What's wrong.** CoreLogic is V1 PsyNFT's `core`. After §0a/§0b the Safe owns V1 PsyNFT,
CoreLogic and PsycSale. So even after V2 becomes canonical, a Safe transaction could still call
`mintNextBatch()` (21 new V1 seats) and `createSaleBatchPsycSale()`, which sells them through V1
PsycSale. That would create a parallel, confusing seat set.

**Fix.** Step 8 of the §4d batch is `CoreLogic.updatePsyNftAddress(V2)`. Every CoreLogic mint,
approve and kick path then calls V2, where CoreLogic has no role, and reverts. V1 minting is then
switched off; turning it back on would take a deliberate 2‑of‑4 Safe transaction.

**Tests.** `test_FullCutoverThroughRealSafe` proves that `mintNextBatch` and `kick` revert through
the real Safe afterwards (`GS013`) and that the V1 counter is unchanged.

### UI‑7 (Medium, operational): Safe support was claimed but not built · FIXED

**What's wrong.** The README said to connect the Safe via WalletConnect. The app only supported an
injected wallet: no WalletConnect and no Safe Apps SDK. Owner actions, which belong to the Safe,
had no supported path through the panel.

**Fix.** Every role-gated card now has **Export for Safe** and **+ Safe batch** buttons. Each first
simulates the call as the address currently holding that role (e.g. the Safe), so a revert shows
before anything is exported. It then writes a Safe Transaction Builder file, or collects calls into
a batch with a bottom bar and one download.

**Verified.** In the browser, a slash-less URI was refused during simulation, then the corrected
call was added to the batch.

### PNFT‑02 (Low): no revocation · FIXED
**Fix.** New `revokeTransfer(uint256)` (`onlyCoreContract`) emits `TransferApprovalRevoked`.
**Tests.** `test_PNFT02_*`, invariant I6 (no escalation) and a real-Safe day‑2 rehearsal.

### PNFT‑03 (Low): unchecked finalize counters · FIXED
**What's wrong.** `finalizeMigration` is one-shot and irreversible. A typo in `previousFibonacci_`
(e.g. 210 instead of 21) would permanently distort, or gas-brick, the schedule.

**Fix.** It now requires `(previousFibonacci_, nextTokenId)` to be consecutive Fibonacci terms of
the schedule (2/3 … 21/34 …). V1's real values (21/34) pass.

**Tests.** `test_PNFT03_RejectsTypos`, fuzzing, and invariant I2: the live counters are always a
schedule pair.

### PNFT‑04 (Low): base URI footgun · FIXED
**What's wrong.** `tokenURI = baseUri + id`, so a missing `/` breaks all art.

**Fix.** A non-empty URI must end with `/`; an empty string is still allowed. `setBaseUri` also
emits ERC‑4906 `BatchMetadataUpdate(0, max)`, and `supportsInterface(0x49064906)` returns true, so
marketplaces refresh art after the META‑1 re-pin and after future batches.

### OPS‑03 (Low): the freeze is a toggle · MITIGATED
**What's wrong.** `CoreLogic.switchRageQuit()` flips the flag rather than setting it. Executing the
freeze batch twice re-opens V1 ego death.

**Mitigation.** It is pinned by `test_FreezeBatchIsAToggle`. The runbook warning and the signer
checklist require checking `rageQuitAllowed() == true` before signing. V1 code can't be changed, so
this is mitigated rather than fixed.

### OPS‑04 (Low): hand-typed Safe batches · FIXED
**What's wrong.** Signers would have typed eight calls by hand and signed what their device showed
(blind signing).

**Fix.** `script/lib/CutoverCalls.sol` is the single source of truth for every Safe batch (§0a, §0b,
§1, §4c, §4d; §0a added 2026-10-14). `script/SafeBatches.s.sol` writes Transaction Builder files plus `CHECKLIST.md`, which
holds every call and the **expected safeTxHash** for each signer to compare on their hardware wallet.
`test_OffchainSafeTxHashMatches` proves the off-chain hash equals the Safe's own.
`test/SafeRehearsal.fork.t.sol` executes the very same bytes through the real Main Safe. The §0a,
§0b and §1 files are already generated (`safe-batches/`, expected Safe nonces 141, 142 and 143).

### HOLD‑1 (Info): one holder can't receive via `safeTransfer` · DOCUMENTED
**What we found.** 10 of the 33 holder addresses are EIP‑7702-delegated EOAs. Nine delegate to
MetaMask's `EIP7702StatelessDeleGator`, which implements `onERC721Received`. The holder of
**token 29** (`0x453c…38bb`) delegates to an `EIP7702Contract` that does not.

**Impact.** Migration is unaffected, because it uses `_mint`, which has no receiver hook. But
`transferNFTs` (core distribution) and `safeTransferFrom` *to* that address would revert. To send it
a seat later, use approve + `transferFrom`, or ask the holder to update their delegation.

## 3. Cutover / exit‑pool sweep review (W4)

**Sources reviewed.** The verified V1 Treasury and CoreLogic implementations were fetched from
Blockscout into `reference/v1-live/`. `reference/PsyNFT.v1.sol` was confirmed identical to the
on-chain verified V1 source.

**Treasury findings:**
- **Payout.** `exit(id, n, user)` pays `rageQuitBalance / (n − psyNFT.totalTokensBurnt())`. With
  `n = 1` and V2 `totalTokensBurnt == 0`, the payout is exactly the pool: divide by 1, no rounding
  dust. If V2 had burned anything before the batch, the subtraction would underflow and the whole
  batch would revert. It fails safe.
- **Money owed to past exiters.** `withdrawUserFunds` pays `userBalances[msg.sender]` and reduces
  `pendingBalances` by the same amount. What past exiters are owed (0.0943 ETH, token 0) is keyed to
  their own address and untouched. This is asserted against live state.
- **Reentrancy.** `exit` and `withdrawUserFunds` are `nonReentrant` and `whenNotPaused`. The ETH goes
  to the Safe, whose fallback handler can't re-enter usefully.
- **Owner withdrawal.** `withdrawFundsAsPsyDao` can only take ETH above `pendingBalances +
  rageQuitBalance`. There is none today (the Treasury balance equals pool + owed), which is why the
  `exit` route is the only way out.

**Safe findings:**
- **Main Safe.** Safe v1.3.0 (canonical L1 singleton `0xd9Db…9552`), 2‑of‑4, no modules, no guard,
  no fallback handler, nonce 141, about 46.09 ETH.
- **Canonical addresses.** The CompatibilityFallbackHandler `0xf48f…e5e4` and MultiSendCallOnly
  `0x40A2…130D` were confirmed canonical against `safe-global/safe-deployments`. Batches use
  MultiSendCallOnly through DELEGATECALL; every inner step is a CALL from the Safe.
- **Atomicity.** A failing step (e.g. a missing fallback handler) reverts the entire
  `execTransaction` (`GS013`), and the nonce is not consumed (`test_SweepBatchIsAtomic`).
- **Real-Safe rehearsal** (`test_FullCutoverThroughRealSafe`, live state, 2026‑10‑11), a simulation
  on a mainnet fork:
  - the EOA handover, then §0b, §1, deploy + migrate, §4c and §4d all execute through the real Safe
    contract using the addresses of 2 of its 4 owners (approved-hash signatures; no signer signed
    anything). Since 2026-10-14 it runs the three Step 0 handovers and §0a first (see the Addendum);
  - the Safe receives exactly **3.110298529411764706 ETH**;
  - `pendingBalances` is unchanged and every holder keeps their seat;
  - V1 can no longer be minted or kicked;
  - day‑2 operations work: approve a wallet move, revoke, allocate a batch‑7 seat, update metadata,
    and a governed burn.

## 5. Property-based testing (W3)

**Fuzz tests** (`test/AuditOct2026.t.sol`):
- the controlled-transfer gate over window × elapsed time × recipient × controls on/off × operator;
- approval replacement timing;
- arbitrary migrations;
- `finalize` counter pairs.

**Invariants** (`test/invariant/PsyNFTV2.invariant.t.sol`). A random-action handler plays owner,
core, treasury, four members and an outsider. It runs 256 sequences × 100 calls, with
`fail_on_revert = true` and zero handler reverts. Seven properties hold after every call:

| # | Property |
|---|---|
| I1 | Supply accounting: live tokens = minted − burnt |
| I2 | The counters are always a Fibonacci schedule pair |
| I3 | The owner is never zero, and always the expected address |
| I4 | Every member transfer's outcome matches the specified gate exactly |
| I5 | Approvals are single-use |
| I6 | No privilege escalation from non-role addresses (14 privileged functions tried) |
| I7 | Contract-held tokens never carry an operator approval |

Two handler bugs were found and fixed while building the suite: a cheat-code "prank" consumed by a
view call, and seed overflow. Coverage counters prove each path really executes.

## 6. Mutation testing

`audit/2026-10/mutation/mutate.py` generates 178 single-point mutants of the contract:
- removed `require`s;
- flipped comparisons, logic and negation;
- dropped modifiers;
- deleted state writes and events;
- constant, boolean and arithmetic swaps.

Each mutant runs against the full deterministic suite in isolated copies, after a baseline guard
(the unmutated contract must pass first). Results:

| Run | Score | Survivors |
|---|---|---|
| 1 | 86.5% | 24 → 16 test gaps fixed (TEST‑1) |
| 3 | 94.4% | 2 boundary survivors fixed |
| **Final** | **95.5%** (170/178) | 8, all equivalent: |

1. **`nonReentrant` dropped on `migrateBatch`.** No external call is possible, because `_mint` has no
   receiver hook.
2. **`>` → `>=` in the migration-ceiling update.** It assigns the same value; a no-op.
3. **`nonReentrant` dropped on `initialMint` and `batchMintInFibonacci`** (2 mutants). The only
   external call is `onERC721Received` on the contract itself, which is `pure`.
4. **`nonReentrant` dropped on `rescueERC20`, `rescueERC721` and `rescueETH`** (3 mutants). These are
   `onlyOwner`. A re-entering token or recipient is not the owner, so it can't reach any owner
   function. The guards are defense in depth.
5. **`&&` → `||` in the `_update` approval clearing.**
   - On mint, `from == 0` and no approval can exist for an unminted id (`approveTransfer` requires
     `id < tokenId`, and migrated ids are minted before any approval is possible).
   - On a transfer, deleting an empty slot is a no-op.
   - So the only difference is gas.

## 8. Residual risks (inherent; for holders to understand)

1. **Trusted roles.** The Main Safe will be owner, core and treasury. It can:
   - mint batches, distribute seats, and approve or revoke moves;
   - **burn any seat without the holder's consent** (the V1 "kick" power);
   - switch transfer controls on or off, and replace the metadata.

   Security is the Safe's 2‑of‑4 signer set. A higher threshold is worth considering. After
   §0a/§0b the Safe also owns V1 PsyNFT, CoreLogic, PsycSale and the V1 Treasury.
2. **Until the Step 0 handovers complete, V1's admin is outside DAO control.** V1 PsyNFT is still
   owned by a former operator wallet (`0xC3aC…e445`), not by the DAO. CoreLogic and PsycSale, which
   the V1 exit depends on, are owned by one individual's wallet (`0x00c1…6061`). Step 0 hands all
   three to the Main Safe and §0a/§0b accept them; until then, their admin functions (including
   upgrades of CoreLogic and PsycSale) are outside DAO control. The handover comes first in the
   cutover sequence, before the bounty, the PSYC vote and the exit window.
3. **The sweep ends the legacy exit right.** After §4d there is no on-chain ego death; the pool sits
   in the Main Safe. This must be stated in the PSYC proposal, together with the exit window.
4. **The snapshot is only as current as the freeze block.** Runbook §1 freezes ego death before the
   snapshot is taken.
5. **Metadata availability** depends on pinning (META‑1). Two services are recommended.

  again. That was wrong: V1 PsyNFT is still owned by a former operator wallet (`0xC3aC…e445`), not
  by the DAO, and CoreLogic and PsycSale are owned by one individual's wallet (`0x00c1…6061`).
  OPS-02 and §8 are rewritten accordingly.
